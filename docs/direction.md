# 产品方向记录：从档案到时间线与记忆

[项目介绍](../README.md) · [使用指南](usage.md) · [开发指南](development.md) · [后续计划](../TODO.md) · [同类项目调研](ecosystem.md)

本文整理 **2026-10-26/27 的一次长对话**（已归档为《分析招聘日程挤压》，会话
`6ae0d90e-aaa0-83ec-8342-2b7459f453bf`）后半段关于 CEOBE 的讨论：两种记忆、两种时间线、
数据契约与 AI 模块的位置。它是**理解与工程化整理**，不是已批准计划；已批准项只看
`TODO.md` 第二节，MCP 的结论见 `TODO.md` 第三节。

## 结论（一页）

1. CEOBE 的下一步不是继续加功能，而是把「档案」变成「可回溯的认识」：**原始档案只读保真，
   时间线与记忆都是衍生数据**，可以重算、可以修正、可以关闭。
2. 聊天记录的价值不只在某句话，而在**观点形成与变化的过程**；因此检索必须能回到原文与时间，
   不能只给结论。
3. 记忆分两种：**历史对话理解**（随时找回「我说过什么、依据是什么」）与**长期个人记忆**
   （提炼并持续更新「哪些信息现在仍然有用」）。前者可先做、可验证，且是后者的证据基础。
4. 时间线也分两种：**历史档案时间线**（原始消息时间戳，客观）与**事件／观点发展时间线**
   （AI 辅助整理，可修正）。前者是后者的证据基础；两者结合就是「从事件看聊天，从聊天看事件」。
5. 工程上记忆与 AI 可以独立、体验上再整合；CEOBE 核心不引入模型依赖。MCP 是**对外接口**，
   不是产品核心，当前**已评估、暂不做**。

## 一、两种记忆

| | 历史对话理解 | 长期个人记忆 |
|---|---|---|
| 回答的问题 | 我过去究竟说过什么、依据是什么 | 哪些过去的信息对现在仍然有用 |
| 输入 | 完整档案（按需检索） | 检索结果 + 提炼规则 |
| 验证方式 | 单次查询即可对原文验证 | 需要持续使用才能发现过时／失真 |
| 主要风险 | 检索遗漏、只引用片段 | 把「至少目前」固化成永久结论、AI 推断被当成用户事实 |
| 与档案的关系 | 只读 | 只能作为衍生数据，可修正、可丢弃 |

原则：**原始档案是证据，长期记忆是基于证据形成的、允许被修正的认识。** 两者不能同等地位；
记忆条目要保留来源、时间、原文链接与修订历史；用户直接陈述、AI 推断、未验证假设要分开。

## 二、两种时间线

### 历史档案时间线（先做，不依赖 AI）

- 数据源：**消息自己的 `created_at`**，不是会话的 `created_at`／`updated_at`；
- 实测（新归档的《分析招聘日程挤压》）：会话 `created_at` 是 2026-10-28 01:02:06，
  而首条消息是 10-26 21:41:15、末条是 10-28 00:57:29——会话时间其实是**分享链接创建时间**，
  比末条消息还晚，不能拿来排时间线；
- 三类时间要分开显示与使用：消息时间（主）、会话／分享创建时间（辅助信息）、归档时间
  （`captured_at`，说明「什么时候存下来的」）；
- 只用阅读页可见的轮次（新档案 167 条线性消息里有 45 条隐藏记录，不进时间线）；
- 交互：按年／月聚合，点条目跳到会话或消息锚点；空日期如实标注，不猜。

### 事件／观点发展时间线（后做，AI 辅助）

- 事件时间 ≠ 记录时间：可能 10 月 15 日回忆 9 月 29 日发生的事，时间线要能分别表示；
- 每条事件保留：发生时间（可模糊到月／区间）、信息来源会话与消息、置信度／是否 AI 推断；
- 冲突不覆盖：不同聊天对同一事件的描述不一致时保留两份，让人判断；
- 每条都能跳回原文；AI 的解释可以被修改，原始聊天不动。

## 三、数据契约：谁消费什么

| 格式 | 定位 | 已有 | 缺口 |
|---|---|---|---|
| Markdown | 人读、Obsidian | frontmatter、角色、段号、时间、附件相对路径 | 消息级 ID、完整日期（同日只写时分秒）、附件本体 |
| 官方格式 JSON（`export:json`） | 机器读、跨工具 | 节点／消息 ID、`content.raw`、线性顺序、附件路径、时间 | 不导出 `raw_payload`，缺失附件只计数 |

建议：**记忆／语义项目消费 JSON**（消息锚点、时间、顺序齐全），MD 保持阅读语义；
不要为了让 AI 好用来改 canonical JSON；导出格式是两边的稳定契约，改动先补测试。

## 四、AI 放在哪里

- 体验上整合、工程上解耦：统一的阅读界面可以显示事件与记忆，但 AI 能力作为**可选模块**，
  默认关闭；模型、向量索引、记忆更新规则不进入 CEOBE 核心；
- 衍生数据单独存放（建议 `data/private/` 下的独立命名空间或独立项目），**绝不写 `archive/`**；
- 隐私：接云模型即意味着档案正文外发，必须显式开启并说明；本地模型也要能完全关掉；
- 任何 AI 结果都要能回链原文，且允许「重新整理 → 覆盖衍生数据」而不触碰原始档案。

## 五、MCP 的位置（已评估、暂不做）

- 讨论中的结论：MCP 是让外部工具访问档案的**通道**，不负责形成记忆；它适合作为检索／记忆能力的
  薄适配层，而不是 CEOBE 的核心目标；
- 当前不做四工具版 archive MCP 的理由：`export:json` + `search-index.json` 已覆盖「把档案交给
  其它工具」；真正缺的是检索质量与时间线；MCP 接云客户端是持续的正文外发面，需要显式 opt-in；
- 将来若做：等检索／记忆内核出现后，只暴露 `search_history` 与 `read_conversation_context`
  这类带原文引用的工具，只读、本地、默认关闭。详见 `TODO.md` 第三节。

## 六、候选路线（未批准，按价值排序）

1. **历史档案时间线 v1**（不依赖 AI）：构建期生成时间线索引（会话 → 首末消息时间、每日轮数），
   新页面按年／月浏览并跳转；验收：条目数 = 会话数、排序 = 首条消息时间、两次构建字节一致、
   不碰 `archive/`。
2. **数据契约收尾**：明确「人读 MD、机读 JSON」；如记忆项目只吃 MD，再补消息锚点与完整日期。
3. **事件时间线原型**（独立进程／独立仓库）：消费 JSON，产出带来源指针的衍生数据；
   CEOBE 只负责导入并渲染衍生时间线，不执行推理。
4. **长期记忆**（更后）：在事件时间线稳定后，加入记忆条目、来源、修订历史与纠错界面。

## 七、测试案例（现成的）

- **事件链**：鹰角 28 届实习（发现岗位 → 准备作品集 → 10/10 投递 → 10/26 截止延期 → 等待结果）；
- **观点演变**：这篇聊天里「先凭记忆评价 CEOBE，后经 MCP 看仓库改口」的过程，正好验证
  「保留修正过程」而不是只留结论；
- **自指案例**：CEOBE 自己的开发史（为什么选 JSON 作数据源、何时产生时间线／记忆想法）
  是第一份可以拿来验证「事件／观点时间线」的真实材料。

## 八、明确不做

- 把 AI 续聊、云端共享、登录态采集加回来；
- 让 AI 生成物改写 `archive/` 或 canonical JSON；
- 把 MCP 当作产品核心目标，或用它替代检索内核；
- 为了方便 AI 而牺牲阅读体验或数据保真（例如把分支、隐藏记录裁掉）。

## 九、开放问题（需要作者拍板）

- 时间线先做会话级还是消息级？（建议先会话级 + 日／月聚合，再做消息级）
- 事件／观点时间线是否进主仓库，还是独立项目？
- 数据契约是否冻结在 `export:json` v1？MD 是否补消息锚点？
- AI 模块的隐私默认值：默认关闭、只用本地模型，还是允许用户显式连接云模型？
