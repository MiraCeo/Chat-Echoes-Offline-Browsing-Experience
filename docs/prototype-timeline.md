# 聊天时间轴原型（P1–P7）

只读设计原型，用来比较“会话节点 / 日期节点”两种定位，以及“基础 / 进度条”两种编码。
它不进入正式页面、不参与生产构建，也不改写 `archive/`；正式 `timeline.html` 与列表视图不受影响。

## 生成与查看

```powershell
npm run prototype:timeline
```

输出 `data/private/timeline-prototypes/index.html`，直接双击打开；顶部标签或 `?v=p1`…`?v=p7`
切换变体。数据来自 `replay/public/timeline-index.json` 与 `replay/chats.json`（当前 36 个会话，
2026-07～2026-10，构建机本地时区）；新增会话后先跑 `npm run library`，再跑原型生成。

## 八个变体

| 变体 | 定位 | 编码 | 不编码 |
|---|---|---|---|
| **P1 会话基础** | 横轴上每个节点=一条会话，卡片上下交替 | 先后顺序 | 真实间隔、跨度、重叠 |
| **P2 会话进度** | 同 P1，卡片内加逐日进度条 | 整条=该会话自身跨度，每格一天，填充=有消息（如 2/3） | 跨会话绝对时长（所有条等宽） |
| **P3 日期基础** | 横轴上每个节点=一个有会话的日期，日期等距 | 日期定位；日期节点分支挂当天会话（按开始时间，标注持续天数） | 真实日历比例、空日期占位；不做缩放 |
| **P4 日期进度** | 同 P3，卡片内加逐日进度条 | 日期定位 + P2 的逐日填充 | 跨会话绝对时长；空日期 |
| **P5 卡片泳道** | 真实日历 96px/天；白色标题卡按日期格拉伸，3 条泳道 | 一整天=一个日期格；节点前/后各 40%，左右留 10%；多天覆盖完整起止日 | 缩放；条内缺口 |
| **P5A 分离泳道（对照）** | 仍用 P3 的事件日期节点 + 上方卡片堆叠；跨度条在下方 3 条泳道 | 卡片/条前后各 40%；同泳道不重叠 | 横轴不是真实日历；卡片与条要编号对应 |
| **P6 缩略图** | 真实日历 7px/天；全档案一屏、3 条泳道、多色细条 | 全档案密度/跨度；月份宽度=天数；颜色仅用于区分会话 | 卡片文字、单日细节；缩放 |
| **P7 整合** | P6 缩略图在上、P5 详情在下，带视口框 | 缩略↔详情的双向定位与同步滚动 | 尚未接正式页面；P5A 不参与 |

P1/P2 是**会话定位**：一条会话一个节点。P3/P4 是**日期定位**：只有有会话的日期才有一个节点，
日期之间等距；P4 的日期卡片用逐日格子表达“当天这条会话持续了几天、哪几天有消息”。

**P5 详情**改成真实日历：96px/天，铺满 2026-07～10 的完整日期（123 天，空日期也占位）；
白色标题卡按日期格拉伸，节点前/后各 40%（左右留 10% 间隙），3 条泳道互不交叉。

**P5A** 是对照组，仍用 P3 的 33 个事件日期节点（155px/节点）和卡片堆叠；它故意不改成真实时间，
否则两张图的横轴不可比。如果 P5A 以后转正，应该和 P5 一起加时间比例。

**P6 缩略图**按真实日历 7px/天铺满完整月份（7/8/10 月各 217px、9 月 210px）；3 条泳道、多色细条、
无卡片文字。颜色按会话从 12 色板循环分配，仅用于区分；相邻条留 1px 缝隙。

**P7 整合**把 P6 放在上方、P5 放在下方：缩略图带视口框，滚动详情同步视口；点击或拖动缩略图
定位详情。详情 96px/天、缩略 7px/天，两者共用真实日历坐标。

当前数据：36 条会话、真实日历 123 天、P5 3 条泳道；P2/P4 的进度条共 99 个格子、77 个填充。

## 已观察到的取舍

- **P1** 最干净、最像“时间线”，但横轴只是等距槽位，不回答“隔了多久、覆盖多长”。
- **P2** 在不增加新轴的情况下补上了“跨度 + 缺口”：23 天跨度、5 天有消息的会话会是一条长条里
  5 个深格和 18 个浅格；代价是所有条等宽，表达比例而不是绝对时长，长跨度的格子会很细。
- **P3** 日期节点让“同一天有几条会话”非常直观，也自然跳过没有会话的日期；代价是没有空日期占位，
  看不出“中间停了多久”。日期节点按首条消息日期归属，跨天会话只在开始日出现一次。
- **P4** 把 P2 的进度条放进日期卡片，既能按日期找，又能看单条会话的持续与缺口；但卡片更拥挤，
  9px 的元信息偏小。
- **P5** 真实日历 96px/天，白色标题卡按日期格拉伸：节点前/后各 40%（居中 80%，左右留 10%），
  36 张卡片、3 条泳道、0 交叉；详情层最完整，代价是初始最左侧可能截到更早开始的会话。
- **P5A** 保留 P3 的卡片堆叠（33 个事件日期节点），卡片/跨度条按前后 40% 留间隙；代价是横轴不是
  真实日历，同一会话要上下两处找对应，结束日只有节点没有卡片。
- **P6** 真实日历轴（7px/天，月份宽度=天数）：能看密度、跨度与空档分布；多色+1px 缝隙让相邻条
  可区分，但没有文字、没有单日细节，适合作为详情页上方的缩略导航，而不是主阅读视图。
- **P7** 把 P6/P5 叠成一页：缩略视口框 ↔ 详情滚动双向同步，点击/拖动缩略图可定位详情；它证明
  “缩略 + 详情”可以共用同一套真实日历坐标，但还没有接正式页面。
- 共同问题：P1–P4 一屏只放 4 张会话卡（36 条需要横向拖动约 8,300px）；月份标签只在每月第一张卡
  上方，滚到月中就看不到；P2/P4 的“格子缝隙”和“空格”需要更清楚地区分；P5–P6 的初始左侧截断/空日期
  还需要和正式页面一起处理。

## 还需要定的事

1. 正式时间线用**卡片泳道**（P5）为详情、**缩略图**（P6）为导航，还是整合页（P7）直接作为产品；P5A 是否只作对照；
2. 日期节点按“首条消息日期”还是“当天有消息”（跨天会话会出现在多个日期）；
3. 日期之间：等距跳过空日期，还是按日历留白；
4. 时间轴方向：最新在右（当前）还是最新在左；初始是否停在最新；
5. 空日期、月份刻度、图例、缩放、窄屏退化（是否改单列）怎么做；
6. 是否作为 `列表 | 时间轴` 的第二视图，保留现有列表为默认。

看过 P1–P7 之后再定；在这之前不改正式页面的数据与交互。
